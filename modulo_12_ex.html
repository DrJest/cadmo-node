2. Hash, JWT e "che cosa succede?"

Hash veloci e hash lenti

input è una funzione async che riceve crypto e bcrypt. Confronta sha256 e bcrypt, guarda dentro un hash, misura il costo. Ctrl+Invio esegue.

Dentro un JWT

Un token firmato con HS256, decodificato e verificato qui nel browser. Cambia il ruolo senza firmare (il server lo rifiuta), poi firma di nuovo: se il segreto è quello giusto il server ci crede. Per questo il segreto deve restare segreto (e lungo). Puoi anche incollare il token della Biblioteca 9.0: il suo segreto è nel file .env del progetto.

🎯 Quattro domande sul JWT (con le risposte)
  1. Cancella l'ultimo carattere della firma: che errore dà il server?
  2. Cambia il ruolo con il pulsante 😈: che cosa vede il server? E l'header e il payload sono ancora leggibili?
  3. Cambia il segreto in "segreto" e premi ✍️: il token ora vale? Per quale server?
  4. Che cosa ci guadagna un attaccante a cambiare "alg": "HS256" in "none", se il server non passa algorithms a jwt.verify?

1. invalid signature (→ 401): la firma non corrisponde più a header e payload.

2. Sempre invalid signature: il payload è cambiato ma la firma no. Header e payload si leggono comunque (sono solo base64url): niente dati segreti nel token.

3. Sì, ma solo per un server che usa "segreto" come JWT_SECRET. Chi conosce il segreto può fabbricare token per chiunque e con qualunque ruolo: va tenuto in .env, lungo e casuale.

4. Con alg: none un token non ha firma. jsonwebtoken lo rifiuta comunque se c'è un segreto, ma l'opzione algorithms: ['HS256'] mette in chiaro che l'algoritmo lo sceglie il server: è la regola contro tutta una famiglia di attacchi "di confusione dell'algoritmo".

<script>
  let accessToken = null;                      // in memoria: non in localStorage
  const out = (x) => (document.querySelector('#out').textContent = JSON.stringify(x, null, 2));
  async function io() {
    const r = await fetch('/api/auth/io', { headers: { Authorization: `Bearer ${accessToken}` } });
    out(await r.json());
  }
  document.querySelector('#login').onsubmit = async (e) => {
    e.preventDefault();
    const r = await fetch('/api/auth/login', { method: 'POST', headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(Object.fromEntries(new FormData(e.target))) });
    if (!r.ok) return out(await r.json());
    ({ accessToken } = await r.json());
    io();
  };
  document.querySelector('#rinnova').onclick = async () => {
    const r = await fetch('/api/auth/refresh', { method: 'POST' });   // il cookie parte da solo
    if (r.ok) { ({ accessToken } = await r.json()); io(); } else out(await r.json());
  };
</script>
// 3. refresh: HttpOnly ✓, SameSite=Strict, Path=/api/auth, scade tra 7 giorni (Secure solo in produzione).
//    document.cookie non lo mostra: è HttpOnly. Ed è visibile solo sulle richieste a /api/auth.
// 4. Il browser allega il cookie da solo (stesso sito, path giusto): il JavaScript non deve conoscerlo.
//    Dopo un riavvio funziona ancora: il refresh token è un JWT firmato e la versione sta in MongoDB.
//    (Con le sessioni di express-session nel MemoryStore, invece, un riavvio fa uscire tutti.)

Missione B: "solo i miei prestiti" e il cambio password

Focus: autorizzazione sulla proprietà, verifica della vecchia password, invalidare le sessioni

  1. Aggiungi GET /api/auth/io/prestiti: i libri con un prestito aperto dell'utente del token (il filtro usa req.utente.id, non un parametro dell'URL).
  2. Permetti a un lettore di restituire (DELETE /api/libri/:id/prestito) solo i suoi prestiti; la bibliotecaria può restituirli tutti. Che status dai a Giulia che prova a restituire il libro di un altro?
  3. Aggiungi PATCH /api/auth/password con { vecchia, nuova }: controlla la vecchia, salva la nuova (passando da save(), non da updateOne: perché?) e chiudi le altre sessioni.
// routes/auth.js — 1. i miei prestiti: l'utente viene dal token
router.get('/io/prestiti', autentica, async (req, res) => {
  res.json(await Libro.find({ prestiti: { $elemMatch: { utente: req.utente.id, al: null } } }).select('titolo prestiti.$'));
});

// routes/libri.js — 2. restituire: la bibliotecaria tutto, il lettore solo i suoi
router.delete('/:id/prestito', autentica, valida({ params: idParam }), async (req, res) => {
  const filtro = { _id: req.valido.params.id, 'prestiti.al': null };
  if (req.utente.ruolo !== 'bibliotecario') filtro['prestiti.utente'] = req.utente.id;
  // (meglio ancora: prestiti: { $elemMatch: { al: null, utente: req.utente.id } }, così le due condizioni valgono per LO STESSO prestito)
  const libro = await Libro.findOneAndUpdate(filtro, { $set: { disponibile: true, 'prestiti.$.al': new Date() } }, { returnDocument: 'after' });
  if (!libro) throw new NonTrovato('Nessun tuo prestito in corso per questo libro');   // 404: non riveliamo i prestiti altrui
  res.json(libro);
});
// (un 403 andrebbe bene lo stesso: 404 nasconde anche il fatto che il prestito esista)

// routes/auth.js — 3. il cambio password
router.patch('/password', autentica, async (req, res) => {
  const { vecchia, nuova } = z.strictObject({ vecchia: z.string(), nuova: z.string().min(8).max(72) }).parse(req.body);
  const utente = await Utente.findById(req.utente.id).select('+password +versioneToken');
  if (!(await utente.verificaPassword(vecchia))) throw new NonAutenticato('Password attuale sbagliata');
  utente.password = nuova;          // save() → validazione + pre('save') → hash
  utente.versioneToken += 1;        // i refresh token di tutti i dispositivi non valgono più
  await utente.save();
  res.cookie('refresh', refreshToken(utente), opzioniCookie);    // questo dispositivo resta dentro
  res.json({ accessToken: accessToken(utente) });
});
// con updateOne({ password: nuova }) l'hook pre('save') NON gira: nel database finirebbe la password in chiaro
