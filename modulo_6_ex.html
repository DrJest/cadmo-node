Ogni script fa una serie di richieste a un server REST e stampa qualcosa. Clicca le righe nell'ordine in cui compaiono nel terminale (alcune possono comparire più di una volta, altre mai!).

3. Biblioteca 3.0

La biblioteca è diventata un'API REST vera: versione nell'URL, CRUD completo, filtri, ordinamento, pagine, 405 e 409, e il catalogo nel file data/libri.json, che vedi cambiare sotto il log. Il pulsante ↻ riavvia il server mantenendo i file; quello con il database rimette i dati iniziali.

PUT {{base}}/libri/{{nuovo.response.body.$.id}}
Content-Type: application/json

{ "titolo": "Sostiene Pereira" }

DELETE {{base}}/libri/{{nuovo.response.body.$.id}}

### Metodo non permesso → 405 + Allow
DELETE {{base}}/libri

# 2. dopo la POST:

# [nodemon] starting `node server.js`
# nodemon osserva anche i file .json della cartella: il server ha scritto
# data/libri.json e nodemon lo ha riavviato. Qui non si perde niente (i dati

# 3. due soluzioni equivalenti

# 4. con require('./data/libri.json'):
#    - node --watch riavvia il server a ogni POST: il file ora è un modulo "osservato";
#    - con node server.js il file si legge UNA volta (cache di require): le POST lo
#      scrivono, ma l'elenco resta quello dell'avvio finché non riavvii.
#    Morale: per dati che cambiano, fs.readFile a ogni richiesta (o un database).

Missione C: Venti POST nello stesso istante

Focus: richieste contemporanee, lost update, coda delle scritture

  1. Con il server della missione A acceso, crea stress.mjs: manda insieme 20 POST (con Promise.all), stampa gli status e poi quanti libri con autore Stress Test ci sono nel catalogo.
  2. Lancialo un paio di volte (node stress.mjs): arrivano 20 risposte 201? Nel catalogo ci sono 20 libri nuovi? Ci sono id ripetuti? Qualche 500?
  3. Spiega che cosa è successo, disegnando su un foglio due richieste che si "accavallano" (leggi → modifica → scrivi).
  4. Correggi il server con una coda: le operazioni che scrivono vengono eseguite una alla volta. Rilancia lo script.
// stress.mjs — 20 POST contemporanee (.mjs: qui await si può usare fuori da una funzione)
const url = 'http://localhost:3000/api/v1/libri';

const risposte = await Promise.all(
  Array.from({ length: 20 }, (_, i) =>
    fetch(url, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ titolo: `Libro di prova ${i}`, autore: 'Stress Test' }),
    }),
  ),
);
console.log(risposte.map((r) => r.status).join(' '));

const elenco = await (await fetch(`${url}?autore=stress&limite=50`)).json();
console.log('Libri "Stress Test" nel catalogo:', elenco.totale);
console.log('Id:', elenco.dati.map((l) => l.id).join(', '));

// Risultato tipico (cambia a ogni esecuzione): molti 201, forse qualche 500,
// ma nel catalogo ne restano MENO di 20 e alcuni id si ripetono.
// Più richieste leggono lo stesso file, ognuna aggiunge il suo libro e riscrive:
// l'ultima che scrive cancella il lavoro delle altre ("lost update").
// I 500 arrivano quando due richieste rinominano lo stesso libri.json.tmp.
// server.js — una coda: ogni scrittura parte solo quando la precedente è finita
let coda = Promise.resolve();

function inCoda(operazione) {
  const risultato = coda.then(operazione);
  coda = risultato.catch(() => {});   // un errore non deve bloccare la coda
  return risultato;
}

// nella POST (e allo stesso modo in PUT, PATCH e DELETE)
.post(async (req, res) => {
  const dati = scegliCampi(req.body);
  if (!dati.titolo || !dati.autore) throw creaErrore(400, 'titolo e autore sono obbligatori');
  const libro = await inCoda(async () => {
    const libri = await leggiLibri();
    // ... controllo dei doppioni ...
    const nuovo = libroCompleto(Math.max(0, ...libri.map((l) => l.id)) + 1, dati);
    libri.push(nuovo);
    await salvaLibri(libri);
    return nuovo;
  });
  res.status(201).location(`/api/v1/libri/${libro.id}`).json(libro);
})
// Ora: 20 × 201, 20 libri, id tutti diversi. Funziona con UN processo:
// con più server (o più istanze) serve un database con le transazioni (modulo 9).
